# 绝区零 Windows 桌面电量小组件

设计版本：2026-10-19。本文保留产品方案与实现约束；后续已完成 WPF Windows 客户端、米游社官方网页登录入口和独立可执行程序。实际功能、运行方式及验证边界以 [使用说明](../README.md) 为准。

## 1. 产品定位

一眼看清“还有多少电量、什么时候回满”的桌面伴侣。核心是电量，今日便笺按需展开。默认静默常驻，避免占据任务栏或打断游戏。

首版面向 Windows x64 和用户自己的米游社国服角色；其他区服与账号体系列入后续兼容验证。原生 Windows 工程位于 src，发布程序位于 dist；原逆向资料及 Python 演示保留供参考。

采用独立无边框桌面窗口。微软提供的 Windows Widgets 目前显示在 Widgets Board 中，需要唤出面板，与这里的常驻桌面体验不同。[微软 Widgets 概述](https://learn.microsoft.com/en-us/windows/apps/design/widgets/)

## 2. 外观与信息层级

保留原版的电池图标、深色表面和亮色强调，把电量数字做大。酸橙绿为默认强调色，可切换原版亮黄；跟随系统提供炭黑、浅灰两套表面配色。

不采用闪烁、循环扫描线或常驻角色动画。角色背景可作为后续皮肤；首版优先保证不同桌面背景上的读数清晰度。

### 三种呈现

| 形态 | 建议逻辑尺寸 | 内容 |
| --- | --- | --- |
| 标准卡片，默认 | 宽 340 DIP，高约 280 DIP，自适应内容 | 游戏标识、当前电量 / 上限、分段进度、回满倒计时与时刻、同步状态 |
| 迷你电量条 | 宽 288 DIP，高约 84 DIP | 电池图标、当前电量 / 上限、回满时刻、展开入口 |
| 展开便笺 | 宽 340 DIP，高随条目增长 | 标准卡片 + 今日活跃 + 服务端下发便笺 |

尺寸为逻辑单位，不锁死物理像素。实际高度由字体、缩放及内容决定。支持 100%、125%、150%、200% 缩放，长条目换行而非覆盖数值。

### 信息顺序

1. “168 / 240”：当前电量为视觉中心，上限弱化；上限始终读取接口。
2. “7 小时 12 分后回满” + “今天 22:30”：帮助用户安排上线时间。
3. “15:18 同步”：表明数据新鲜度；本地推算、离线和过期时有明确标记。
4. 点击“今日便笺”展开日常状态；条目名及顺序由接口决定。

预览中的电量、时间及便笺全部是示例。固定以 15:18 为示例时刻，不代表实时服务器数据。

低电量不标红：体力已使用通常无需紧张。接近回满、已回满使用琥珀色提示。实际电量超过自然恢复上限时照实显示，如“280 / 240”，进度条保持满格，提示“自然恢复已暂停”。

## 3. 桌面交互

| 操作 | 结果 |
| --- | --- |
| 拖动标题区域 | 移动窗口，靠近屏幕工作区边缘时吸附 |
| 点击刷新 | 合并并发请求；冷却期间显示可重试时间 |
| 点击缩小 | 切换迷你条，保留同一锚点 |
| 点击“今日便笺” | 展开 / 收起，不触发网络请求 |
| 点击设置 | 打开非模态设置面板，Esc 关闭 |
| 托盘单击 | 显示 / 隐藏组件 |
| 托盘右键 | 刷新、尺寸、置顶、锁定、穿透、设置、退出 |

默认不抢焦点，不占据任务栏按钮；保留可发现的系统托盘入口。窗口与设置支持键盘和辅助功能。

“始终置顶”默认关闭。普通窗口模式允许其他应用遮住组件；开启后才保持在其他普通窗口上方。全屏游戏时可自动隐藏，属于待验证的系统行为。

“锁定位置”只禁止拖拽，不等于鼠标穿透。鼠标穿透是单独的高级设置，只能在托盘入口工作正常时启用；用户始终可以从托盘关闭穿透。每次重启检查窗口是否仍处于已连接显示器的工作区内。

“贴在壁纸层、Win+D 后继续显示”是另一个实现要求。普通无边框窗口不能保证这一点。首版实现可拖动的常驻窗口；若要真正嵌入 Explorer 桌面层，需独立验证不同 Windows 版本、显示桌面、Explorer 重启和多显示器行为，再决定是否启用，不能把它与置顶混为一谈。

## 4. 提醒与设置

首版设置保持简单：尺寸、外观、置顶、位置锁定、提醒、开机启动、当前角色、退出登录。开机启动和通知由用户在应用中自行开启。

提醒默认关闭；可选“回满前 30 分钟”和“回满时”。每个账号、角色及恢复周期各提醒一次；启用前选定的两个时间点分别去重。按系统通知权限和勿扰设置展示，不抢占前台。

回满时刻因游戏消耗发生明显变化后开启新的恢复周期；休眠后过期提醒不补发成串通知。数据离线、登录失效、过旧或时间异常时暂停提醒，先校准数据。托盘文本仍显示当前状态。

后续可增加“启动游戏”，但需要用户选择实际 Windows 启动程序或已验证的启动器协议。现有 Android nap://launch 不能直接视为 Windows 的有效启动方式。

## 5. 登录和数据状态

### 首次使用

连接米游社 → 在官方页面或受支持的扫码流程完成登录 → 验证凭据 → 获取并选择绝区零角色 → 成功读取第一份便笺 → 显示桌面组件。

扫码登录作为待验证的优先体验。仓库中的二维码创建、轮询、Token 获取与换票流程没有在本次任务中实测。浏览器登录也必须验证 Cookie 的域、有效性与所需凭据类型；检测到账号 ID 不等于具有读取接口的权限。

登录窗口关闭即可取消；二维码有过期时间；轮询可取消且有超时。用户不需要把 Cookie 发给任何人。凭据写入当前 Windows 用户作用域的 DPAPI 加密存储；设置和数据缓存分开保存。[微软数据保护说明](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection)

### 状态矩阵

| 状态 | 主数字 | 辅助说明 | 行为 |
| --- | --- | --- | --- |
| 尚未连接 / 无成功缓存 | — / — | 连接米游社 | 不用 0 或演示数据占位 |
| 首次同步 | — / — | 正在读取电量 | 允许取消，不显示虚假的实时数值 |
| 同步成功 | 服务端数值 | 同步时间 | 保存带账号、角色身份的快照 |
| 本地恢复估算 | 推算值 | “估算”及上次同步时间 | 不宣称读取到游戏内即时消耗 |
| 网络异常且缓存仍新 | 推算值 | 离线估算 | 保留数据、退避重试、暂停提醒 |
| 缓存超过 60 分钟 | 最后一次服务器数值 | 数据已过期 | 停止整数推算，保留原始同步时间 |
| 登录过期 | 最后一次服务器数值 | 登录已过期 | 暂停轮询，用户主动重新连接 |
| 需要验证 / 限流 | 最近可信记录 | 请完成验证 / 稍后重试 | 暂停或按服务端要求退避，不绕过验证 |
| 没有角色 / 权限未开启 | — / — | 明确缺少什么 | 引导用户在米游社检查角色或便笺权限 |
| 电量回满 / 超过上限 | 如 240 / 240、280 / 240 | 自然恢复已暂停 | 保留真实数值，不强行裁成上限 |

本地估算只包含自然恢复，无法知道玩家刚刚消耗电量、喝咖啡或领取奖励。预览里正常状态展示的是刚同步的示例快照，离线场景展示估算标记。

## 6. 同步与计算规则

### 频率

- 启动、手动刷新、网络恢复、系统唤醒可触发同步；所有触发共用一个调度器。
- 默认 15 分钟同步一次，加少量随机抖动。它是初始产品配置，不是官方频率保证。
- 两次请求至少间隔 60 秒，并合并相同角色的进行中请求；尊重服务端限流及 Retry-After。
- 普通网络失败按 1、2、5、15 分钟退避；登录失效和验证要求不持续重试。
- 可见时每分钟更新恢复文字，隐藏时停止纯展示定时器；没有逐秒网络请求。
- 唤醒、系统时间跳变、网络恢复先校准；保留缓存时明确其时间和状态。

降低请求频率只能减少无谓请求，不能保证“零风控”。现有 PollingStrategy.md 中的固定资源占用、零风险等说法没有测量证据，不作为验收结论。

### 不可变快照

保存 accountKey、roleKey、服务端当前值 C、上限 M、恢复剩余秒数 R、接收时刻及进程内单调时钟锚点。UI 不原地递减快照。

单次运行中，从时间锚点计算经过时长，不按“定时器回调执行次数”累计秒数。进程重启、休眠和系统时钟变化时重新校准；跨进程单调时间值不可直接复用。

仓库假定自然恢复周期为每点 360 秒。实现时将其作为可验证的协议配置，优先使用服务端的剩余秒数；不在本次设计中断言该机制永不变化。

当 0 ≤ C < M、R > 0 且 R 与周期一致时：

~~~text
Δ = 360 秒 / 点（待在线验证）
r = max(0, R - elapsed)
E = max(C, min(M, M - ceil(r / Δ)))
回满时刻 = 快照接收时刻 + R
~~~

这样能保留“下一点电量只剩一部分恢复时间”的相位。例：C=238、M=240、R=450 时，89 秒后仍为 238，90 秒后为 239，450 秒后为 240。

验证恢复周期的一致区间：理想情况下 (M-C-1)×Δ < R ≤ (M-C)×Δ；允许小范围传输和取整容差。明显不一致时只显示服务端值及倒计时，停止整数推算并记录脱敏诊断信息。

R 缺失、非法，或 C<M 却 R=0，不直接判定满电。C≥M 时保留 C，停止自然恢复估算；进度条比例单独限制在 0–100%。跨天显示“明天”或日期，避免只显示时分。

## 7. 技术落地建议

正式客户端建议 **C# + WPF + .NET 10 LTS**。WPF 的矢量布局、数据绑定和 Windows 适配符合小型常驻窗口需求；现有 Python 代码保留作协议研究和结果比对。WPF 是 Windows 专用框架，非跨平台方案。[WPF 官方说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)

截至本设计日期，.NET 10 为 LTS，支持到 2028-11-14；原文档建议的 .NET 8 将于 2026-11-10 结束支持，因此新项目优先选择 10。最终系统兼容范围按选定运行时和实机验证确定。[.NET 支持周期](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)

| 模块 | 职责 |
| --- | --- |
| Desktop | WPF 窗口、托盘、显示器定位、设置及通知 |
| Application | 账号与角色选择、状态机、刷新调度、取消任务 |
| Domain | 不可变电量快照、时间估算、数据新鲜度及提醒去重 |
| Infrastructure | HTTP、接口 DTO、凭据保护、缓存及日志 |
| Tests | 计算边界、状态切换、协议样本与少量桌面集成测试 |

界面层只消费统一状态，不自行拼请求头。HTTP 调用可取消、有超时；同一角色只允许一个请求进行。切换角色时取消旧任务，并用角色标识及请求版本阻止迟到响应污染当前界面。数据缓存按账号和角色隔离。

Windows 通知、开机启动、托盘、穿透、高 DPI、全屏检测需要实际工程验证。安装包尺寸、工作集内存、CPU 占用取决于打包及渲染方式，本次没有给出实测数值。

## 9. 开发顺序与验收

1. **先验证数据链路**：在用户主动登录后，取得本人角色的成功响应；核对电量、恢复时间、角色归属、鉴权错误及新鲜度。敏感字段不写日志。
2. **实现最小桌面版**：标准 / 迷你形态、拖动和位置记忆、托盘、手动与周期刷新、可区分的离线 / 过期状态。
3. **完善桌面体验**：提醒去重、高 DPI、多显示器、唤醒校准、开机启动；最后处理桌面层嵌入与可选皮肤。

必须覆盖的验收场景：

- 恢复边界 89/90/450 秒示例，R=0 异常、字段缺失、超过上限及跨日。
- 连点刷新只产生一条进行中请求；界面响应不因网络等待卡住。
- 登录失败或断网保留真实缓存，不自动填充演示数据；账号切换无缓存串用。
- 电脑休眠后恢复时重新校准，不用遗漏的定时器回调计算电量。
- 多屏切换和拔掉显示器后，能从托盘找回窗口。
- 100%–200% 缩放下无文字遮挡；键盘可操作设置和展开按钮。
- 通知在同一恢复周期不重复；失去可信数据后不继续发“电量满了”。

本次交互预览仅验证外观及局部交互。同步按钮更新示例反馈；置顶、提醒、锁定等开关只保存预览选择，不操作 Windows。
